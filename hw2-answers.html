3(a)

Disk read: mode and process switch because the caller blocks. Disk completion for a lower-priority process: mode switch only; current process continues. Division by zero followed by termination: mode and process switch because the terminated process cannot resume.

3(c)

A mode switch changes privilege level to run kernel code. A process switch also saves registers, updates PCBs and queues, selects another process, updates memory-management information, and restores the selected process’s context.

4(a)

Process identification: process ID, parent process ID, user ID. Processor state information: program counter, stack pointer, general-purpose registers, program status word. Process control information: process state, scheduling priority, awaited event, next-PCB pointer, open files, memory-table pointers, privileges.

4(b)

Processor state information must be saved whenever the process stops running so it can resume correctly. Skipping this could restore an incorrect program counter, stack pointer, or register value and cause a crash or incorrect results.

5(d)

The terminated child is a zombie until reaped. The kernel retains its PID, exit status, and accounting information for the parent to retrieve with wait(); ordinary memory and most resources are released.

6(a)

Pure ULT: when T1 blocks in read(), the whole process blocks, so T2–T4 cannot run; at most one thread executes at once; the user-space library schedules threads. Pure KLT: only T1 blocks; the others remain eligible; at most two execute at once on two cores; the kernel schedules threads.

6(b)

ULT: 1500×3 µs = 4500 µs = 0.0045 s per second; utilization = 0.0045×100 = 0.45%. KLT: 1500×45 µs = 67500 µs = 0.0675 s; utilization = 6.75%. Processes: 1500×700 µs = 1050000 µs = 1.05 s; utilization = 105%. Process creation alone exceeds one core’s capacity, so it cannot sustain this rate.

6(c)

Jacketing wraps potentially blocking calls with readiness checks or nonblocking operations. When an operation would block, the library runs another user-level thread, avoiding a block of the entire process.

B-b

The three threads have the same PID, 41580, and PPID, 4476, but different native thread IDs: 12088, 38376, and 43772. The three processes have different PIDs, 51556, 9712, and 18348, and different native thread IDs, 19596, 3812, and 37036. All three processes have PPID 41580, the main process. A process owns its address space and resources, while threads are independently dispatched units that share their process's resources.

B-c

The thread shares the main process's global list, so its append remains visible as ['main', 'thread']. Windows uses spawn, which starts the child with a fresh copy of the program and an empty SHARED list. Therefore the child prints ['process']. Its changes affect only its own address space, and the main list remains ['main', 'thread'].

B-e

The GIL was enabled. Threads showed almost no CPU speedup: 1.80 seconds with one worker versus 1.77 seconds with eight workers, a reported speedup of 1.02. Processes improved from 1.87 seconds to 0.35 seconds, a reported speedup of 5.37. For CPU-bound Python code, GIL-limited execution resembles the one-at-a-time behavior of pure ULTs, although these are real kernel threads and blocking I/O can release the GIL. Each process has its own interpreter and GIL, so separate processes can execute Python computations on several cores.

B-f

Using the displayed four-process speedup S=3.46:
f=(1−1/S)/(1−1/4)=(1−1/3.46)/0.75=0.947977≈0.948.
Predicted S(8)=1/((1−0.947977)+0.947977/8)=5.8644≈5.86.
The program reports f=0.949 and predicted speedup=5.88 because it uses unrounded timing measurements. Measured eight-process speedup=5.37, which is below the prediction. Pool startup, interprocess communication, and scheduling overhead do not necessarily follow a fixed serial fraction; background work and CPU frequency changes can also distort individual measurements. The system reports 32 logical CPUs, which are not necessarily 32 equally fast physical cores.

B-g

One thread took 2.01 seconds; eight threads took 0.25 seconds. Speedup from the displayed times = 2.01/0.25 = 8.04. The small difference from eight is timing overhead and rounding. A sleeping thread blocks and releases the GIL, allowing the kernel to schedule other threads while the waits overlap. This helps the waiting workload, whereas CPU-bound Python threads barely sped up because the GIL permits only one to execute Python code at once.
