3(a)

getpid(): mode switch only; caller resumes. Clock with time left: mode switch only. Expired time slice: mode and process switch to another ready process. Disk read: mode and process switch because the caller blocks. Disk completion for a lower-priority process: mode switch only; current process continues. Division by zero followed by termination: mode and process switch because the terminated process cannot resume.

3(c)

A mode switch changes privilege level to run kernel code. A process switch also saves registers, updates PCBs and queues, selects another process, updates memory-management information, and restores the selected process’s context.

4(a)

Process identification: process ID, parent process ID, user ID. Processor state information: program counter, stack pointer, general-purpose registers, program status word. Process control information: process state, scheduling priority, awaited event, next-PCB pointer, open files, memory-table pointers, privileges.

4(b)

Processor state information must be saved whenever the process stops running so it can resume correctly. Skipping this could restore an incorrect program counter, stack pointer, or register value and cause a crash or incorrect results.

6(a)

Pure ULT: when T1 blocks in read(), the whole process blocks, so T2–T4 cannot run; at most one thread executes at once; the user-space library schedules threads. Pure KLT: only T1 blocks; the others remain eligible; at most two execute at once on two cores; the kernel schedules threads.

6(b)

ULT: 1500×3 µs = 4500 µs = 0.0045 s per second; utilization = 0.0045×100 = 0.45%. KLT: 1500×45 µs = 67500 µs = 0.0675 s; utilization = 6.75%. Processes: 1500×700 µs = 1050000 µs = 1.05 s; utilization = 105%. Process creation alone exceeds one core’s capacity, so it cannot sustain this rate.

6(c)

Jacketing wraps potentially blocking calls with readiness checks or nonblocking operations. When an operation would block, the library runs another user-level thread, avoiding a block of the entire process.

B-e

The GIL was enabled. Thread times stayed near 2.9 seconds, showing essentially no CPU speedup. Process time fell from 2.85 seconds to 0.52 seconds with eight workers. For pure Python CPU work the GIL-limited process resembles the one-at-a-time execution of pure ULTs, although its actual threads are kernel threads and blocking I/O need not stop them all. Each process has its own interpreter and GIL, so separate processes can compute on several cores.

B-f

Using the displayed 4-process speedup S=3.03: f=(1−1/S)/(1−1/4)=(1−1/3.03)/0.75=0.89329. Predicted S(8)=1/(1−0.89329+0.89329/8)=4.5779≈4.58. Measured S(8)=5.46. The program uses unrounded times, so its f may differ slightly. Two explanations are noisy CPU scheduling/clock speed between measurements and pool startup/communication overhead that does not scale as a fixed serial fraction. Nine reported logical CPUs do not guarantee nine equally fast, fully available physical cores.

B-g

One thread took 2.00 seconds; eight took 0.25 seconds. Ratio=2.00/0.25=8.00. A waiting thread blocks rather than calculating, so other threads can run and their waits overlap. The GIL is released during sleep, unlike the CPU loop, so threads help this waiting workload.
